# 方法：先对抗，再暂停，再录音

AI 写代码越来越快，返工的原因变成了：代码没写错，只是写的不是同一件事。需求方脑子里的需求，和研发读到的需求，常常差一截。

核心一句话：**在 AI 动手写代码之前，先让人把认知对齐；对齐的过程，交给一段视频来主持。**

## 四步

### 1. 各自复述（会前）

研发用自己的 AI 读需求文档，写一份"我理解的需求"。不抄原文，用自己的话写出页面、流程、状态、接口依赖和待定问题。

### 2. 对抗比对（会前）

需求方把这份理解交给自己的 AI，逐条和需求原文比对，输出分歧清单。每条写清**五要素**：

| 要素 | 字段 | 说明 |
|---|---|---|
| 需求原文怎么说 | `req` | 引用原文位置 |
| 研发怎么理解 | `dev` | 引用复述稿位置 |
| 不对齐的风险 | `risk` | 不定下来会出什么事 |
| 建议的最小修法 | `fix` | **建议，非共识** |
| 本次要定什么 | `decide` | 一个能回答的问题 |

分歧 ≠ 错误。常见类型：新旧确认冲突、已定事项被重新列为待定、"界面不做某按钮"被误读成"能力不做"、资料没读到。

> 类比：需求写"用户可以取消订单"，研发稿写"暂不做取消按钮"。没有按钮，不等于没有取消能力。

### 3. 视频主持（会上）

- 分节，每节有建议时长；
- 一个分歧一屏：左需求、右研发理解，下面风险、建议、本次要定；
- 讲完弹"请暂停视频"，讨论出结论再继续；
- 底部分节进度条标出每个暂停点，可跳转；
- 开场写明规则：已定事项不重新投票；技术事实由研发拿证据；结论按口令说。

### 4. 录音回填（会后）

结论口令：

> 已定：「A07，决定：……；理由：……；负责人：……；下一步证据：……」
> 未定：「A07，暂缓；在等：……」

录音转文字 → AI 按编号抽取口令 → 生成**待确认**回填表 → 人确认后再更新需求文档和开发计划。

## 为什么让视频主持

- **节奏固定**：每项有时间盒；
- **不漏项**：进度条一直摆在那里；
- **规则不被带偏**：开场规则写死在视频里，不因为谁嗓门大改口；
- **建议和共识分开**：屏幕上的修法都标"建议，非共识"；
- **主持人也能参与讨论**，不用一边控场一边想问题。

## 实战数据（一场真实会议，已脱敏）

| 指标 | 数值 |
|---|---|
| 分歧数 | 20 项，分 5 节 |
| 暂停点 | 23 个 |
| 视频时长 | 11 分 42 秒 |
| 计划 / 实际会长 | 60 / 98 分钟 |
| 从清单到成片 | 约半小时，大半在等渲染 |
| 增量改版 | 关 1 项、换 1 道挑战题，只重配 8 句旁白 |

## 会后学到的

1. **全程走完、没漏项**——视频解决了"不跑题、不漏项"。
2. **时间超了**——时间盒按条数平均分太乐观。真正卡住的往往是两三个核心问题，下次按难度分配时间。
3. **口令没人用**——但大家会自然说"回到 A06，这个的结论是……"。**编号 + "结论是"就够 AI 抽取**，不必强求完整句式。
4. **视频旁白会混进转写**，多出一个"说话人"。整理前先把主持提示和真实决定分开，否则 AI 会把建议当成决定。
5. **会后闭环跑通了**：AI 从录音直接整理出需求补充稿，人确认后分发到各端待办。
